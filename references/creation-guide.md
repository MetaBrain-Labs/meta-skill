# 创建新 skill

把 skill 创建为可复用的流程，而不是一次性的回答。

skill应是渐进披露，不应该一次展示所有内容。

## 必要结构

```text
skill-name/
├── SKILL.md          # 必须
├── references/       # 可选，存放详细文档
├── scripts/          # 可选，存放确定性工具
├── assets/           # 可选，存放模板/资源
└── evals/evals.json  # 推荐
```

## Frontmatter 规则

`SKILL.md` 必须以 YAML frontmatter 开头：

```markdown
---
name: skill-name
description: 当用户需要... 时使用本 skill。
---
```

`name` 只能包含小写字母、数字和连字符；必须与目录名一致。

`description` 应简洁且聚焦于触发场景，说明何时使用本 skill，而不仅仅是描述 skill 是什么。

## 编写流程

1. 用一句话说明 skill 的职责。
2. 定义激活上下文：明确触发短语、相关短语，以及用户可能不直接命名该领域的情况。
3. 定义预期输出。
4. 识别应封装为脚本的确定性子步骤。
5. 识别适合放入 `references/` 的长篇或条件性内容。
6. 编写简洁的 `SKILL.md` 主体，包含工作流、默认值、边界条件和校验循环。
7. 添加 2-3 个贴近真实用法的 eval 提示词。
8. 校验。
9. 修复。
10. 打包。

## 描述模板

```text
当用户需要 [主要目标] 时使用本 skill，包括 [具体场景]。适用于 [关键词和相关术语]，尤其是任务需要 [专项工作流] 时。不适用于 [容易混淆的场景]，除非 [特定条件]。
```

## 主体模板

```markdown
# Skill 标题

一句话说明运作目的。

## 工作流

1. 理解输入和约束。
2. 选择合适的路径。
3. 只运行或编写必要的文件。
4. 校验输出。
5. 报告结果和注意事项。

## 默认值

- 默认使用 X。
- 只有 X 无法满足任务时才使用 Y。

## 边界条件

- 如果缺少输入，推断安全默认值，或仅在卡住时提问。
- 如果校验失败，修复后重新运行。

## 输出格式

[具体模板]
```

模板中各小节并非每个 skill 都要全配齐。最小可用的 skill 只需"工作流"一节；更复杂的 skill 才视情况扩展。

## 写作原则

**解释原因，而不是堆砌强制约束。** 当你准备写下"必须""不要""一定要"时，先停下，把背后的理由表述出来。例如，与其写"不要执行第三方脚本"，不如写"第三方 skill 在审查前是不可信代码，因此审查阶段不运行其脚本、不安装其依赖"。前者是命令，后者是原则——遇到未列举的边界场景时，原则可以指引推断，命令则无法覆盖。

**使用祈使语气，但保留弹性。** 祈使句简洁直接、便于阅读，但不必每一句都设为强制约束。过度刚性的指令反而会限制模型在复杂场景下做出合理判断。

**不要为单个示例过度拟合。** skill 迭代时只能校验几个示例，但 skill 后续可能被运行成千上万次。如果某条规则只是为了让其中一个用例表现得更好，应先评估该用例在其他用例上是否可能产生负面影响。

**description 应当具有明确触发性。** 大模型常具有"少触发"倾向——明明应使用某个 skill 却没有触发。因此 description 不仅要说明该 skill 做什么，还要说明在哪些场景下应主动联想到该 skill，特别在用户未使用专业术语的情形。同时给出"不适用于"的反向边界，可以减少误触发。

## 何时添加脚本

当同一个确定性操作会被反复重新实现时，应封装为脚本：校验、打包、解析、转换、报告生成或代码检查。

脚本应自包含、提供清晰的错误信息，并避免隐式的网络调用，除非用户明确请求在线检索。

## 何时添加 references

将内容移入 `references/` 的条件：内容较详细、有条件性、并非始终需要。在 `SKILL.md` 中明确说明何时读取该引用文件。

不好的写法："详情见 references。"

更好的写法："仅当 API 返回非 2xx 响应时，读取 `references/api-errors.md`。"
